# 센서 기반 통합 차량관리 서비스 기본 요구사항

버전: 0.4 · 작성일: 2026년 10월 26일 · 갱신일: 2026년 11월 7일(앱 1.2.7 기준) · 서비스명: 미리정비

차량 센서에서 관측되는 변화와 사용 환경, 정비 이력을 함께 분석해 관리가 필요한 항목과 점검 시점을 알려주는 Pleos Connect 차량용 앱을 기획한다. 운전자는 정비 지식이 부족해도 내 차에서 무엇이 달라졌는지, 왜 안내가 나왔는지, 다음에 무엇을 해야 하는지 이해할 수 있어야 한다.

이 문서는 전체 서비스의 기본 요구사항과 구현 범위를 정의한다. 요구사항은 기획안이며, 부품 상태 추정의 실차 정확도가 검증되었다는 뜻은 아니다. 공모전·SDK 공개 자료는 2026년 10월 26일 수집본을, 차량 신호 접근 범위는 11월 2~3일 에뮬레이터 실측을 기준으로 한다. 지금 앱이 실제로 하는 일과 수치는 [1단계 안내](../docs/phase1-maintenance.md)가 기준이고, 이 문서와 다르면 그 문서를 따른다.

차량 그래픽 중심의 홈, 부품 상세 확대, 질문을 하나씩 받는 첫 설정과 등록 후 상태 확인은 [차량 중심 UX 기획](ux-concept.md)에 구체화했다.

| 항목 | v0.3 | v0.4 (현재 구현) | 바꾼 이유 |
| --- | --- | --- | --- |

| 권장 주기 | 사용자가 개월 프리셋이나 직접 입력으로 알림 간격을 정함 | 인식한 차종의 취급설명서 주기를 자동 적용(6개 차종 14개 동력원, 전기차는 엔진오일 제외) | 차가 제조사·차종·연식·연료를 알려 줘 설명서 주기를 바로 쓸 수 있다. 주기를 아는 운전자는 드물다 |

| 일시정지 | 모니터링 일시정지(새 수집 중지) | 부품별 알림 일시정지. 알림과 챙길 개수에서만 빼고 판정과 수집은 그대로 | 알림을 끈 부품이 정상으로 보이면 안 된다 |

## 1. 해결할 문제와 대상 사용자

차량 관리는 주행거리나 기간에 따른 교체 알림만으로 실제 사용 부담과 성능 변화를 충분히 반영하기 어렵다. 운전자는 성능 저하를 느껴도 어느 항목을 점검해야 하는지, 교환 시점이 가까운지 판단하기 어렵고, 부품별 정비 이력도 흩어져 있다.

초기 대상은 Pleos Connect 지원 개인 차량을 운행하며 정비 시점 판단에 어려움을 느끼는 운전자다. 초기 버전은 차량 한 대의 관리 흐름에 집중한다. 내연기관·하이브리드·전기차에 따라 적용할 수 있는 관리 항목을 달리한다.

서비스가 제공할 가치는 다음과 같다.

- 사용 조건과 실제 관측 변화를 반영한 관리 안내
- 부품별 상태와 교체·점검 이력을 한곳에서 확인하는 경험
- 관측 근거와 판단 한계를 함께 설명하는 점검 제안

## 2. 서비스 범위

제안한 여섯 관리 영역을 전체 서비스 범위에 포함한다. 각 영역은 지원되는 데이터와 검증 수준에 따라 순차적으로 제공한다.

| ID | 관리 영역 | 제공하려는 기능 | 판단에 필요한 입력 후보 |
| --- | --- | --- | --- |
| MON-01 | 와이퍼와 앞유리 | 닦임 성능 저하 징후, 와이퍼 마모·유막 관련 점검, 교체 시점 안내 | 레인센서 신호, 와이퍼 동작과 사용량, 강우·기온, 교체·유리 관리 이력 |
| MON-02 | 엔진과 엔진오일 | 평소 대비 운전 특성 변화, 사용 부담과 오일 열화 관련 점검 안내 | RPM·토크·출력·속도·기어·온도, 운행 시간·거리·조건, 오일 교체 이력 |
| MON-03 | 브레이크 | 제동 사용 부담과 변화 추세, 패드 점검·교체 관련 안내 | 제동 상태·압력·토크, 감속·속도·경사·적재 조건, 회생제동 기여량, 패드 정비 이력 |
| MON-04 | 타이어 | 사용 조건에 따른 마모 추세와 점검 필요성 안내 | 휠 속도·차량 운동·공기압·노면·날씨, 주행거리, 교환·위치 교환 및 실측 마모 이력 |
| MON-05 | 냉방과 난방 | 작동 후 온도 응답 변화, 냉난방 성능 저하 징후, 관련 계통 점검 안내 | 실제 온도·설정 온도·풍량·내외기·창문 상태, 외기·일사·구동계 조건, 정비 이력 |
| MON-06 | 실내 공기와 필터 | 공조 작동에 따른 공기질 변화와 정화 성능 추세, 필터 점검·교체 안내 | 공기질 센서 종류별 측정값, 풍량·내외기·외부 오염·습도, 필터 교체 이력 |

입력 후보는 필요성을 검토할 목록이다. 모두 Pleos에서 제공된다는 뜻은 아니며, 모델별 최소 입력과 선택 입력은 데이터 검증 후 정한다. MON-01의 와이퍼 마모와 유막, MON-02의 엔진 이상과 오일 열화, MON-05의 냉매·히터 등 세부 원인도 구분 가능한 근거가 있을 때만 개별 판단한다. 냄새 분석은 적합한 센서와 검증 근거가 확보되는 경우에만 추가한다.

차량을 직접 제어하는 기능, 실제 결제, 다수 차량을 운영하는 사업자 관리, 추가 하드웨어 개발은 초기 범위에서 제외한다. 정비 예약은 시연용 예시 업체로 흐름만 보이고, 실제 제휴처와 결제는 출시 전에 붙인다.

## 3. 사용자 이용 흐름

1. **첫 설정:** 처음 열면 필요한 권한을 이유와 함께 한 화면에서 허용받고, 부품마다 마지막 정비 시점을 대략의 보기로 묻는다. 모든 질문에 "모르겠어요"와 "나중에 할게요"가 있어 일괄 등록을 강요하지 않는다. 차종은 차가 알려 준 정보로 정하고 적용되지 않는 항목(전기차의 엔진오일)은 묻지 않는다.
2. **항목별 등록:** 홈에서 부품을 누르면 그 부품이 가운데로 옮겨 가며 상세로 이어진다. 기록이 없는 부품은 최근 정비 날짜 하나를 받고, 당시 주행거리는 선택으로 둔다. 모르는 이력은 "이력 대기"로 남긴다.
3. **평소 운행:** 등록한 항목에 한해 플랫폼이 허용하는 실행 상태에서 지원 데이터를 관찰한다. 사용자 조작 없이 관측 이력과 사용량을 쌓고 비교 가능한 조건의 데이터를 구분한다. 등록 직후에는 실제 데이터 준비 상태를 표시한다.
4. **변화 발견과 조치:** 반복 관측이나 주기 도래에 따라 관리 항목을 갱신한다. 정차 후 상세에서 변화·판단 근거·권장 행동을 확인하고 직접 확인한 증상이나 점검 결과를 기록한다.
5. **정비 후 추적:** 교체·점검 결과를 기록하고 이전 이력을 보존한다. 정비 이후 관측을 별도 구간으로 관리하며 성능 변화가 개선됐는지 추적한다.

## 4. 공통 기능 요구사항

아래 공통 기능은 초기 버전의 필수 요구사항이다. 기능별 감시 모델은 7절의 도입 조건을 충족한 항목부터 연결한다.

| ID | 요구사항 | 기본 완료 조건 |
| --- | --- | --- |
| FR-01 | 차량 정보와 관리 항목을 설정한다 | 차종·연식·동력원·주행거리 등 필요한 정보를 관리하고, 적용되지 않는 항목을 구분한다. 자동 확인값과 사용자 입력값을 구분한다 |
| FR-02 | 항목별 센서 지원과 권한을 확인한다 | 현재 차량·환경에서 사용 가능한 입력을 확인하고, 미지원·권한 부족·일시 오류를 구분해 표시한다 |
| FR-03 | 관측 데이터와 사용 맥락을 기록한다 | 값·단위·측정 시각·출처·수집 유효성을 기록한다. 중단·누락·오래된 데이터가 발생했을 때 정상 관측으로 처리하지 않는다 |
| FR-04 | 차량별 비교 기준을 관리한다 | 비교 가능한 운행·공조·환경 조건을 구분한다. 초기 관측값을 검증 없이 정상 기준으로 확정하지 않으며, 기준 부족은 수집 중으로 표시한다 |
| FR-05 | 여러 근거를 함께 사용해 판단한다 | 지원되는 관측 변화·사용량·기간·거리·환경·정비 이력을 결합한다. 필수 입력이 없거나 적용 조건을 벗어나면 해당 추정을 보류한다 |
| FR-06 | 차량 중심의 통합 상태를 보여준다 | 중앙 차량과 원형으로 배치한 실물 형태의 부품 이미지를 연결한다. 부품 이름과 할 일·거리를 짧게 표시하고, 주기 또는 추정에서 쓴 양을 링으로 표현한다. 퍼센트는 쓰지 않는다. 사각 카드 목록은 사용하지 않는다. 확인이 필요한 항목은 요약과 강조로 먼저 발견하게 하되 카드 위치를 상태에 따라 뒤섞지 않는다. 마지막 유효 관측 시점과 다음 행동은 상세에서 확인한다 |
| FR-07 | 판단 이유와 수준을 설명한다 | 무엇이 달라졌는지, 어떤 조건을 고려했는지, 무엇을 판단할 수 없는지 보여준다. 관측값·추정 결과·주기 안내를 구분한다 |
| FR-08 | 점검·교환주기를 관리한다 | 차종에 맞는 제조사 권장 기준과 교체 이력을 출처와 함께 관리한다. 기준이 없거나 이력을 모르면 미확인으로 표시하고 임의 주기를 확정하지 않는다 |
| FR-09 | 필요한 알림을 제공한다 | 주기 도래 또는 기준을 충족한 변화가 생겼을 때 알린다. 동일 상태를 반복 통보하지 않고, 재알림·확인·나중에 보기 설정을 제공한다 |
| FR-10 | 정비 이력과 사용자 확인을 기록한다 | 항목·날짜·주행거리·점검/교체 내용과 확인 출처를 기록·수정·삭제한다. 이전 관측은 보존하되 삭제 요청 시 관련 보존 정책에 따라 처리한다 |
| FR-11 | 항목별 변화와 정비 전후를 확인한다 | 기간별 관측 요약과 정비 이벤트를 함께 보여준다. 정상화가 확인되지 않았는데 교체 기록만으로 상태를 정상 처리하지 않는다 |
| FR-12 | 수집과 데이터 관리를 사용자가 제어한다 | 수집 목적·대상·저장 범위를 확인하고 수집을 중지할 수 있다. 차량 관리 데이터를 삭제·초기화할 수 있으며, 재개 후 누락 기간을 구분한다 |
| FR-13 | 부품 카드에서 상세로 자연스럽게 이어진다 | 선택한 부품 그림·이름이 확대 상세로 연결되고 닫으면 원래 카드로 돌아온다. 상세와 등록을 겹친 모달로 쌓지 않는다 |
| FR-14 | 항목별 최소 입력으로 등록한다 | 첫 설정은 부품마다 질문 하나와 대략의 보기로 받는다. 엔진오일은 그 뒤 달린 거리를, 브레이크 패드는 점검 뒤 달린 거리만, 타이어는 장착 시점과 그 타이어로 달린 거리를 묻는다. 상세의 기록은 날짜 하나에 주행거리 선택이다. 주기는 차종 권장값을 자동 적용하며 사용자가 알림 간격을 정하지 않는다. 차가 아는 주행거리는 다시 묻지 않는다 |
| FR-15 | 등록 상태와 관찰 결과를 구분한다 | 미등록·작성 중·등록됨·일시정지와 데이터 준비 상태·관리 결과를 별도 관리한다. 등록 완료만으로 정상 판정하지 않으며 미지원 시 이력·주기 관리와 자동 관찰을 구분한다 |
| FR-16 | 등록과 탐색의 진행 상태를 복원한다 | 질문 도중 닫기·프로세스 재시작·창 크기 변경·주행 규제 전환 후 답변과 단계를 보존한다. 금지된 입력을 자동 재개하거나 모니터링을 중복 등록하지 않는다. 현재는 기록 입력 화면의 답만 보존되고, 팝업 안의 입력은 주행 규제로 팝업이 닫히면 사라진다(2차 PT 전 과제) |

사용자가 교체 이력을 입력하지 않아도 지원되는 관측 기능은 사용할 수 있어야 한다. 다만 이력에 의존하는 주기 계산은 제한됨을 표시한다. 제조사 기준보다 점검을 앞당기는 제안은 근거와 함께 제공하고, 검증되지 않은 추정으로 권장 주기를 연장하지 않는다.

## 5. 결과와 알림 표현

**등록 상태·관리 상태·데이터 상태를 별도로 관리한다.** 지원하지 않거나 관측이 끊긴 항목을 정상으로 표시하지 않는다. 홈은 현재 행동에 중요한 상태를 짧게 표시하고, 상세에서 각 상태와 관측 시점을 설명한다.

| 구분 | 상태 예시 | 표시 원칙 |
| --- | --- | --- |
| 등록 상태 | 미등록 / 작성 중 / 등록됨 / 일시정지 | 미등록·등록 완료를 각각 이상·정상 판정으로 표현하지 않는다 |
| 관리 상태 | 현재 관측 범위 내 특이 변화 없음 / 변화 관찰 / 점검 권고 / 정비주기 도래 | 차량 전체의 안전이나 고장 유무를 보증하는 표현을 사용하지 않는다 |
| 데이터 상태 | 관측 가능 / 초기 수집 중 / 데이터 부족 / 일시 중단 / 미지원 | 마지막 유효 관측 시각과 현재 판단 가능 범위를 함께 표시한다 |
| 판단 근거 | 직접 확인한 차량 상태 / 연구 모델에 따른 추정 / 사용량·기간·거리 기반 안내 / 사용자 입력 | 근거 유형과 출처를 확인할 수 있어야 한다 |

알림은 **항목, 관측된 변화, 비교 조건 또는 근거, 권장 행동** 순서로 쓴다. 심각도와 판단 신뢰 수준은 별개로 다루며, 정확도 백분율은 쓰지 않는다. 주기의 몇 %를 썼다는 숫자는 홈과 판단 근거에 쓰지 않고, 추정 범위와 함께 측정값 화면에만 둔다. 실차 측정 논문의 계수로 계산한 마모량(브레이크 패드 잔량, 타이어 홈 깊이)은 "추정"이라고 밝혀 mm로 보여 주고, 계수 범위와 계산 조건(앱이 본 주행 구간, 빠진 요소)은 측정값 화면에 함께 적는다. 판정은 범위의 위험한 쪽을 따른다. 패드 잔량은 패드 교체를 기록한 뒤에만 계산하고, 새 패드 두께는 투싼 정비지침서의 11 mm를 다른 차종에도 가정한다. 타이어 홈 깊이 추정으로는 교체를 권하지 않고 깊이 확인만 요청한다.

예시 문구는 “비슷한 설정에서 냉방 온도 변화가 이전보다 느린 경향이 반복 관측됐습니다. 냉방 성능 점검을 권장합니다.”와 같은 형태다. 이는 문구 예시이며 실제 관측 결과나 검증된 임계값을 뜻하지 않는다.

부품별 성능 저하 원인을 구분할 근거가 부족하면 점검할 계통과 확인 방법을 안내한다. 차량 자체의 경고와 충돌하는 안내는 제공하지 않으며, 차량 경고를 대체하거나 해제하지 않는다.

## 7. 데이터와 연구 근거에 관한 요구사항

11월 2~3일 Pleos 속성 427개와 AAOS 속성 208개를 에뮬레이터에서 직접 읽어 접근 범위를 확인했다. 엔진 회전수·오일 온도는 시스템 전용 권한이라 일반 앱이 읽지 못해 차속과 외기 온도로 엔진 열 상태를 추정한다. 바퀴별 공기압과 TPMS 경고는 비공개 권한을 요구해 월 1회 점검 알림으로 대신한다. Android 표준 조향각은 막혀 있지만 Pleos SDK의 핸들 각도는 열려 있어 타이어 좌우 가속에 쓴다. 앱이 쓰는 신호와 막힌 신호의 전체 표는 [차량 신호 접근 범위](../docs/vehicle-signal-access.md)에 있다. 에뮬레이터가 전기차라 엔진 계열 속성 33개는 실측하지 못했고, 실차에서 의미·단위·주기를 다시 확인해야 한다. [S2][S3]

새로운 감시 기능은 다음 조건을 충족한 뒤 사용자에게 제공한다.

1. 필요한 센서·이력·환경 데이터의 접근과 사용 권한을 확인한다.
2. 값의 의미·단위·시각·수집 주기·누락을 확인하고 최소 입력과 적용 조건을 정한다.
3. 참고 연구의 입력·차종·실험 조건·검증 범위를 기록하고 앱의 조건과 비교한다.
4. 모델의 결과를 실제 점검·측정값과 비교할 방법 및 성능 기준을 정한다.
5. 입력 부족·조건 불일치·오류 시 추정을 중단하거나 더 제한된 안내로 전환한다.

연구에 필요한 데이터가 없는 경우에는 정비주기 관리나 관측 가능한 상태 안내만 제공하고, 이를 마모 측정이나 고장 진단으로 표현하지 않는다. 공기청정 작동 상태를 공기질 수치로, 미세먼지 측정값을 냄새·곰팡이 측정값으로 대체하지 않는다.

차량별 기준선은 현재 관측 상태와 비교하기 위한 값이다. 정상 상태의 확인 없이 정상 기준으로 간주하거나, 느리게 진행하는 열화를 기준선 갱신으로 지워서는 안 된다. 정비 결과와 관측 구간을 연결해 비교 기준의 변경 이력을 관리한다.

## 10. 기본 완료 확인 항목

- 차량 설정 후 관리 항목과 센서 지원 여부를 확인할 수 있다.
- 첫 설정, 부품 선택, 상세, 기록 흐름이 이어지고, 창 크기 변경과 기록 중 중단 후에도 복원된다.
- 기록이 없는 부품에는 추정을 쓰지 않고, 기록만으로 정상 결과를 표시하지 않는다.
- 교체 이력을 모르는 상태에서도 지원되는 관측을 시작하고 제한사항을 이해할 수 있다.
- 지원 입력이 기록되며, 통신·앱 중단이나 누락을 이상 징후와 구분한다.
- 비교 가능한 조건과 충분한 근거가 있는 경우에만 선택한 기능의 판단 결과가 나온다.
- 안내에서 관측 변화·근거·한계·다음 행동을 확인할 수 있다.
- 동일 상태의 알림을 중복해서 받지 않으며 정차 후 상세 내용을 확인할 수 있다.
- 교체·점검 이력을 입력하면 정비 전후 관측이 구분되고, 입력만으로 정상 상태가 확정되지 않는다.
- 수집 중지·데이터 삭제·재시작 이후에도 상태와 이력이 일관되게 처리된다.
- 실제 데이터와 시연 데이터를 명확히 구분해 제시할 수 있다.

기능별 최소 관측량·비교 기간·탐지 임계값·오탐 및 미탐 기준·재알림 간격·원시 데이터 보관 기간은 상세 설계에서 정한다. 근거 없이 수치를 확정하지 않는다.

## 11. 다음 기획에서 정할 항목

- 실차·정비 실측 데이터 확보 방법(정비소 패드 두께·홈 깊이 측정과 앱 추정 비교)
- 공기압·엔진 회전수 등 막힌 신호의 권한 개방 요청 범위
- 관리 영역별 사용자의 점검 행동과 알림 표현
- 기능별 연구 근거 및 재현·검증 계획
- 원시 데이터 보관 범위와 외부 데이터 사용 방식
- 차량 앱 단독 제공 범위와 이후 모바일 연동 필요성

세부 기술·공모전 질문은 [확인할 사항 목록](../materials/05_notes/open-questions.md)에 정리돼 있다. 전체 항목의 정밀 진단을 첫 버전의 완료 조건으로 두지 않으며, 검증 결과에 따라 제공 수준을 정한다.

화면 구조·부품별 등록 질문·상태 문구·전환·예외 흐름과 UX 완료 조건은 [차량 중심 UX 기획](ux-concept.md)을 기준으로 상세 설계한다.
